# 2026.330.1608 — fix(cdp): close resolves its tab reference, and a hung surface capture cannot eat the step

## Summary

Two defects in the `cdp` verb, both found on the KDE-over-VNC pod's live R10 bed
(opencharly/opencharly#1294) and both fixed at the source.

- **`close` now resolves its tab reference like every other method.** `tab: "1"` is the only
  reference a plan can write — no check variable carries a target id between steps, which is why
  every method documents it — but `close` sent it verbatim to `/json/close/` and asked Chrome for a
  target whose id was the literal `1`, getting HTTP 404 on a healthy browser while `cdp: url` and
  `cdp: text` on the same tab passed. The resolution now lives in ONE helper, `resolveTabID`, which
  returns the target itself; `resolveTabWS` builds the WebSocket URL from it and `runClose` closes
  by its id. A non-numeric reference still falls through to an id match.
- **A hung `Page.captureScreenshot` can no longer eat the step.** The plugin hardcoded
  `fromSurface:true`, which on this GPU Wayland Chrome never returns: the step was killed at its
  4m30s never-hang bound while the identical call with `fromSurface:false` returned a PNG at once.
  `runScreenshot` now opens its OWN connection per attempt (the shared one is bound to the step
  context, so a hung call on it could only be abandoned by abandoning the step), tries the surface
  capture for a bounded 20 s, and falls back to the renderer-view capture with the step's remaining
  budget. The method is dispatched before the shared WebSocket connect for exactly that reason.

**What the fallback does NOT fix, and is filed instead:** the view capture comes back uniformly
white on this pod. The fix's contract is "the verb RETURNS a capture within a budget instead of
dying on the clock", and the bed now asserts exactly that; producing a *painted* frame through that
path is a separate capture-pipeline question (opencharly/plugin-cdp#14), not this change's subject.

frame — which (a) cannot and (b) alone would not bound.
